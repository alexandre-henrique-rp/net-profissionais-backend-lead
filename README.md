## Description

[Nest](https://github.com/nestjs/nest) framework TypeScript starter repository.

## Project setup

```bash
$ yarn install
```

## Compile and run the project

```bash
# development
$ yarn run start

# watch mode
$ yarn run start:dev

# production mode
$ yarn run start:prod
```

## Run tests

```bash
# unit tests
$ yarn run test

# e2e tests
$ yarn run test:e2e

# test coverage
$ yarn run test:cov
```

## Docker deployment (single container)

The API runs as a single Docker service (`api`) publishing host port `3000`.
Public traffic arrives through the Cloudflare Tunnel (`cloudflared`), which
forwards directly to `localhost:3000` — there is **no internal proxy and no
slot switching**. Each update recreates the container, so the API is down
for a few seconds while the new container boots and passes the healthcheck.

Rollback uses image tags: every release is tagged
`net-profissionais-backend-lead:<commit sha>` and the last two releases are
recorded in `.deploy/releases` (line 1 = current, line 2 = previous).
`./deploy.sh reverter` starts the previous tag **without rebuilding**; if a
new release fails the healthcheck or the port check, the update tries to
restore the previous release automatically.

PostgreSQL and Redis remain external services; this Compose file does not
create or reset either database. Prepare a production environment file on the
server:

```bash
cp .env.example .env.prod
```

Edit `.env.prod` with production values before deploying. At minimum, configure
reachable `DATABASE_URL`, `REDIS_URL`, and a persistent `JWT_SECRET`. Database
and Redis hostnames must be reachable **from a Docker container**; `localhost`
inside `.env.prod` means the API container itself. Set `CORS_ORIGIN` to the
frontend's public origin. Never commit `.env.prod` or copy it into the image:
Compose injects it at runtime, and `.gitignore`/`.dockerignore` exclude it.

On the server, clone this repository, configure `.env.prod`, and run:

```bash
chmod +x deploy.sh
./deploy.sh
```

The menu offers **Atualizar**, **Reverter** and **Sair**. You can also invoke
the actions directly:

```bash
./deploy.sh atualizar
./deploy.sh reverter
```

Updating uses `git pull --ff-only`, builds a release-tagged image, recreates
the `api` container and waits for the Docker healthcheck plus a real request
on the published port before recording the release. Cleanup removes only old
`net-profissionais-backend-lead` images that no container references — the
current and previous release tags are kept so rollback never needs a rebuild.

Check status and logs with:

```bash
docker compose --project-name net-profissionais-backend-lead ps
docker compose --project-name net-profissionais-backend-lead logs -f api
```

### Database migrations

The regular deploy deliberately does **not** modify the database. Review a
migration for compatibility with both the currently active and candidate API,
take a database backup according to your operations policy, then explicitly
run:

```bash
RELEASE_TAG="$(git rev-parse --short=12 HEAD)" \
  docker compose --project-name net-profissionais-backend-lead \
  --profile migration run --rm api-migrate
```

For zero-downtime releases, use expand-and-contract migrations: first add
backward-compatible schema, deploy code that can use it, and defer destructive
column/type removal until no running release depends on the old schema.

## Observability

In production applications, observability is essential for understanding how your system behaves, detecting issues early, and maintaining reliable performance.

[NestJS Observe](https://observe.nestjs.com) automatically instruments your NestJS application, giving you deep visibility into your system with minimal setup:

- **Distributed tracing:** Follow requests across services and understand how they flow through your system.
- **Waterfall analysis:** Visualize request execution and identify slow operations, bottlenecks, and unexpected delays.
- **Performance analysis:** Analyze application performance in real time and quickly pinpoint areas that need optimization.
- **Metrics:** Track key application and infrastructure metrics to understand system health and performance trends.
- **Logging:** Centralize and correlate logs with traces and other telemetry to make debugging easier.
- **Error tracking:** Detect errors quickly and investigate their root causes with the surrounding context.
- **SLA monitoring:** Track service-level objectives and identify when your application is approaching or exceeding defined thresholds.
- **Alarms and alerts:** Set up alerts for critical errors, performance degradation, SLA violations, and other anomalies so your team can react quickly.

This project is already instrumented. To connect it, run this and approve the code it prints at [observe.nestjs.com/link](https://observe.nestjs.com/link) - signing up for free if you have no account:

```bash
$ npx @nestjs/observe link
```

It writes the app key and secret into `.env` and makes every `nest start` script (`start`, `start:dev`, `start:debug`) load it. In production, set `OBSERVE_APP_KEY` and `OBSERVE_APP_SECRET` in the environment instead.

Or do it by hand: create an application and an API key at [observe.nestjs.com](https://observe.nestjs.com), and set the pair as `OBSERVE_APP_KEY` and `OBSERVE_APP_SECRET` in the environment the app runs in.

The free plan needs no payment details and covers 300,000 events a month. You can also browse the [live demo](https://www.observe-demo.nestjs.com/dashboard) first - the whole dashboard over a busy service's data, with nothing to install.
